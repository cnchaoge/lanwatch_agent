# Check 4 — 组网结构（Topology）

> 状态：Draft v0.1（待超哥 review）
> 用途：MVP 前的 SOP 细化，伪代码看 `checks/topology_pseudo.py`

---

## 一、目标

判定内网组网是否存在**结构性错误**（VLAN/子网/路由错配），不是环路也不是 ARP 欺骗，而是"网本身搭得不对"。

典型场景：
- 默认网关配错（不在本机子网）
- 子网掩码错（/24 写成 /16，导致路由选不上）
- VLAN 划分错（应该隔离的没隔离）
- DNS 服务器指向外网（被劫持或配错）
- 路由表有多条默认路由（负载均衡或配错）

## 二、4 个判断维度

### 维度 A — 到公网跳数（间接信号）

traceroute 8.8.8.8 / 114.114.114.114 各取一次。

| 跳数 | 判定 |
|------|------|
| 1-5 | normal（扁平网络） |
| 6-10 | warning（多层企业网，正常） |
| > 10 | warning（异常绕路）|

**置信度**：低（很多合法场景跳数多）

### 维度 B — 默认网关是否在同子网（**强信号**）

本机 IP/掩码 + 默认网关 IP，看网关是否落在本机子网内。

| 情况 | 判定 |
|------|------|
| 在 | normal |
| 不在 | **critical**（拓扑严重错配，会导致完全无法访问外网）|

**置信度**：高

### 维度 C — DNS 服务器位置

读取本机 DNS 配置（`/etc/resolv.conf` / Windows 注册表 / `ipconfig`）。

| DNS IP 位置 | 判定 |
|-------------|------|
| 在常见内网段（10.x / 172.16-31.x / 192.168.x）| normal |
| 在外网（8.8.8.8 / 114.114.114.114 等公网 DNS）| warning（可能配错 / VPN 环境正常）|
| 在异常段（如 169.254.x / 0.0.0.0）| critical |

**置信度**：中（外网 DNS 可能是 VPN 场景）

### 维度 D — 路由表异常

读取本机路由表，看：
- 是否有 ≥ 2 条默认路由（负载均衡/错配）
- 默认路由的 metric 是否异常高

| 情况 | 判定 |
|------|------|
| 1 条默认路由 | normal |
| 2 条默认路由且 metric 接近 | warning（负载均衡，正常）|
| ≥ 2 条默认路由且 metric 差异大 | warning（错配）|
| 0 条默认路由 | **critical**（无法上外网）|

**置信度**：中

## 三、综合判定决策树

```
            ┌──────────────────────────────────────┐
            │ A: 公网跳数                          │
            │ B: 网关是否在同子网（强）            │
            │ C: DNS 服务器位置                    │
            │ D: 路由表异常                        │
            └──────────────┬───────────────────────┘
                           │
                           ▼
            ┌──────────────────────────────────────┐
            │  B 网关不在子网 OR D 0 条默认路由?   │
            │  （强信号：拓扑严重错配）            │
            └─────┬─────────────────────────┬──────┘
                  │ YES                     │ NO
                  ▼                         ▼
            ┌─────────────┐        ┌──────────────────────┐
            │ CRITICAL    │        │  C 异常 OR D 多路由? │

                                              └─────┘ └────────┘
```

## 四、阈值表

| 维度 | NORMAL | WARNING | CRITICAL |
|------|--------|---------|----------|
| A: 公网跳数 | 1-5 | 6-10 | > 10（仅作辅助，不直接 critical） |
| B: 网关在同子网 | 是 | — | 否 |
| C: DNS 服务器位置 | 内网段 | 公网 DNS | 异常段 |
| D: 默认路由数 | 1 | ≥ 2（metric 接近）| 0 |

## 五、误报场景与对策

| 误报场景 | 特征 | 对策 |
|----------|------|------|
| **多层企业网跳数 5-8 正常** | A=8 正常 | A 最高只到 WARNING，单独不升级 |
| **VPN 场景用 8.8.8.8 做 DNS** | C=外网但正常 | 报告里加"若在 VPN 内可忽略"，让超哥现场确认 |
| **多网卡负载均衡** | D=2 条默认路由 | metric 接近 → 标 WARNING，加"若客户主动配置可忽略"|
| **客户主动指向 8.8.8.8 做 DNS** | C=外网 | 报告里加"是否客户主动配置"提示 |

> **核心策略**：维度 B（网关不在子网）和 维度 D=0（无默认路由）才是硬错误；A 和 C 单独只能给软信号。

## 六、漏报场景与对策

| 漏报场景 | 原因 | 对策 |
|----------|------|------|
| **VLAN 错配但同 IP 段** | traceroute 看到正常 | 本机扫描不到的；v2.0 加"SNMP 读 VLAN 表" |
| **内部 DNS 劫持但不暴露** | DNS 解析结果是错的 IP，但 DNS 服务器 IP 看着正常 | v2.0 加"实际解析测试"（解析 baidu.com 看返回 IP 是否合理）|
| **路由 metric 配错导致绕路** | 维度 A 跳数多，但抓包看不出问题 | 报告加提示"建议客户检查路由器路由表" |

## 八、待超哥拍板的问题

### Q1: traceroute 用 ICMP 还是 UDP？

- **建议**：UDP（更通用，Linux/macOS 默认；Windows 要装 tracert 用 ICMP）
- 跨平台方案：默认 UDP，fallback ICMP

### Q2: 主动探测哪些公网目标？

- **建议**：8.8.8.8 + 114.114.114.114（两个目标取最差值）

### Q3: 内网段范围怎么定？

- **建议**：
  - `10.0.0.0/8`（RFC1918）
  - `172.16.0.0/12`（RFC1918）
  - `192.168.0.0/16`（RFC1918）
  - `100.64.0.0/10`（CGNAT，越来越多家用宽带用）

### Q4: 维度 B 触发 CRITICAL 是否过于激进？

- **反方**：客户可能是跨网段访问合法场景（不常见）
- **支持**：99% 的情况就是配错了

- **建议**：v1 激进（CRITICAL），但报告里加"如客户多网卡/路由场景请忽略"提示

### Q5: 是否需要解析 traceroute 中间的 hop 类型？

- 简单方案：只看跳数
- 复杂方案：识别"运营商 hop" vs "内网 hop"（用 IP 段判断）

- **建议**：v1 只看跳数，v2.0 加 hop 类型识别

## 九、与其他 check 的协同

- **与 loop**：traceroute 高延迟 + 广播风暴 → 多半是环路
- **与 rogue_router**：私接路由 + 默认网关错配 → 拓扑有结构性错误
- **本 check 是"地基"**：其他 3 类问题的报告里可以引用本 check 的"网络路径"作为参考
