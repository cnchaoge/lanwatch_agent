# Check 3 — ARP 欺骗（ARP Spoofing）

> 状态：Draft v0.1（待超哥 review）
> 用途：MVP 前的 SOP 细化，伪代码看 `checks/arp_spoof_pseudo.py`

---

## 一、目标

判定内网是否存在 ARP 欺骗（中间人攻击 / 恶意抢答 / 中毒主机广播）。

## 二、4 个判断维度

### 维度 A — 同一 IP 的 MAC 变化次数（**主信号**）

60 秒抓包内，同一 IP 出现 ≥ 2 个不同 MAC → 强信号。

| 变化次数 | 判定 |
|---------|------|
| 0 | normal |
| 1 | warning（可能是 DHCP 续租 / 主备切换）|
| ≥ 2 | **critical**（来回变 = 欺骗）|

**置信度**：高

### 维度 B — 单 MAC 发 gratuitous ARP 频率

中毒主机通常会高频广播自己（攻击工具默认行为）。

| Gratuitous ARP 数 / 60s | 判定 |
|-------------------------|------|
| < 10 | normal |
| 10-19 | warning |
| ≥ 20 | **critical**（攻击工具典型行为）|

**置信度**：中

### 维度 C — 网关 MAC 时间漂移（**与 rogue_router 维度 D 重叠**）

60 秒内网关 IP 的 MAC 变化次数。

| 变化次数 | 判定 |
|---------|------|
| 0 | normal |
| 1 | warning |
| ≥ 2 | warning（共享信号）|

**置信度**：中（**注**：此维度在 rogue_router 里也算了一次，这里复用结果，不重复判定）

### 维度 D — 攻击工具特征 OUI（弱）

已知攻击工具的特征 OUI（Cain、BetterCAP、Ettercap 部分场景）。

- v1 不做（识别成本高、误报风险大），仅作为后续信号预留

## 四、阈值表

| 维度 | NORMAL | WARNING | CRITICAL |
|------|--------|---------|----------|
| A: 同一 IP 的 MAC 变化次数（60s） | 0 | 1 | ≥ 2 |
| B: 单 MAC Gratuitous ARP 数（60s） | < 10 | 10-19 | ≥ 20 |
| C: 网关 MAC 漂移（60s） | 0 | ≥ 1 | — |

## 五、误报场景与对策

| 误报场景 | 特征 | 对策 |
|----------|------|------|
| **VRRP/HSRP 主备切换** | 网关 MAC 短暂变化（通常 < 5 秒） | 维度 A 不命中（只有 1 次变化）→ 不会升级 CRITICAL；维度 C 单独命中只到 WARNING |
| **DHCP 重新分配 IP** | 某 IP 换 MAC（典型是一次性，不是来回变） | 维度 A = 1 → WARNING，不升级 CRITICAL |
| **笔记本休眠唤醒** | 短暂大量 gratuitous ARP | 维度 B 命中但持续 < 60s → v1 仍会报警；建议报告里加"如最近有笔记本休眠可忽略" |
| **移动设备跨 AP 漫游** | 客户端 MAC 在不同 AP 切换时可能短暂刷 ARP | 维度 A 不命中（漫游通常不换 IP）|

> **核心策略**：抓包窗口 60 秒够长，绝大多数误报（DHCP 续租/主备切换）只发生 1 次 MAC 变化 → 维度 A = 1 → 不升级。

## 六、漏报场景与对策

| 漏报场景 | 原因 | 对策 |
|----------|------|------|
| **低频持续攻击** | 每分钟只发 1-2 个，但持续 1 小时 | 60 秒窗口可能错过；v2.0 考虑加"长窗口统计" |
| **HTTPS 环境无法从应用层验证** | 攻击者篡改 HTTP 不可见 | ARP 层仍可见（本 check 仍有效），但要告诉客户"装 lanwatch_agent 才能持续监控" |
| **攻击者仅对特定目标 ARP 欺骗** | 不广播到整个 VLAN | 维度 A 抓不到；建议 v2.0 加"主动探测网关 MAC 一致性" |

## 八、待超哥拍板的问题

### Q1: 抓包时长 60s 够吗？

- **建议**：60 秒主流量 + 可选 120s（`--long` 模式）

### Q2: 维度 C 与 rogue_router 维度 D 是否重复？

- **建议**：arp_spoof 里**复用** rogue_router 维度 D 的结果，不再独立抓样。两者都用 60 秒采样（rogue_router 是 10 秒，建议升级到 60s 以复用）

### Q3: "MAC 变化次数 ≥ 2"是否过严？

- **建议**：v1 严格（≥ 2 才 critical），宁可漏报也不要误报。误报 ARP 欺骗会让客户恐慌"我们的网络被黑了？"

### Q4: 报告要不要给客户看 MAC 厂商？

- **建议**：给，但加隐私提示（"MAC 信息仅供现场排查用，不写入客户可下载的报告"）

## 九、与其他 check 的协同

- **共享 ARP 抓包**：本 check 与 rogue_router 共享 ARP 抓包 + 分析
- **共享网关注册历史**：本 check 维度 C 与 rogue_router 维度 D 复用
- **触发关系**：若 arp_spoof 报警 → rogue_router 也大概率会报警（中毒主机常伴随假网关）
